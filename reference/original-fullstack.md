# Общее ТЗ на проектирование и разработку full-stack CRM-платформы «Свистоплясово»

## 1. Назначение документа

Необходимо спроектировать и поэтапно разработать full-stack платформу базы отдыха «Свистоплясово».

Платформа должна включать:

1. внутреннюю CRM для ежедневной работы администраторов;
2. единый backend и базу данных;
3. API для CRM;
4. архитектурную основу для подключения многостраничного публичного сайта;
5. архитектурную основу для отдельной технической и контентной админки;
6. систему прав, аудита, уведомлений, финансовых операций и проверки доступности ресурсов.

Главный принцип разработки:

> Каждый этап должен давать работающий вертикальный срез: база данных → бизнес-правила → API → frontend → тесты.

Не допускается сначала создавать декоративный frontend на mock-данных, а затем пытаться «прикрутить backend». Такой подход почти неизбежно приводит к несовместимости интерфейсов, API и предметной модели.

# 2. Требование к работе всех следующих агентов

## 2.1. Не исполнять ТЗ механически

Перед проектированием или реализацией каждого этапа агент обязан:

1. изучить общее ТЗ;
2. изучить архив предыдущего этапа;
3. проверить существующую архитектуру и код;
4. выявить пропущенные сценарии и противоречия;
5. продумать дополнительные улучшения;
6. проверить влияние этапа на frontend, backend, базу данных и будущие интеграции;
7. только после этого формировать конечное ТЗ или приступать к реализации.

Агент не должен считать перечисленный функционал исчерпывающим.

Он обязан самостоятельно анализировать:

* отсутствующие бизнес-правила;
* граничные состояния;
* конфликты данных;
* ошибки пользователей;
* одновременную работу сотрудников;
* права доступа;
* мобильные сценарии;
* производительность;
* безопасность;
* информационную архитектуру и удобство настроек и отображения данных;
* способы последующего расширения.

## 2.2. Разрешённые улучшения

Агент может:

* добавлять недостающие поля и состояния;
* уточнять связи между сущностями;
* предлагать более устойчивую архитектуру;
* добавлять необходимые системные сущности;
* улучшать UX;
* объединять дублирующиеся механики;
* создавать общие компоненты и сервисы;
* менять внутренний способ реализации.

Агент не может без обоснования:

* менять основной стек;
* заменять предметную модель принципиально другой;
* отказываться от route-driven overlay;
* создавать отдельные несвязанные backend-модули для одинаковых данных;
* дублировать бизнес-правила на frontend;
* упрощать функционал до статической демонстрации;
* заменять реальные операции mock-данными;
* заменять дизайн-систему shadcn/ui + preset `bIkezqK` самописной стилизацией.

Все значимые архитектурные изменения должны фиксироваться в `DECISIONS.md`.

## 4.3. Стратегия работы с PostgreSQL

PostgreSQL является единственной базой данных платформы. Она используется во всех окружениях: локальная разработка, автоматизированные тесты, staging и production. Отдельная тестовая СУБД (SQLite или любая иная) не используется ни в каком виде — это исключает целый класс ошибок, связанных с расхождением поведения разных СУБД (конкурентность, блокировки, типы, сравнение строк, JSON, работа с датами, индексы, ограничения).

### Роль тестовой базы данных

Для unit-тестов, где обращение к базе не требуется, база данных не поднимается вовсе — используются fakes/in-memory реализации repository ports на уровне domain/application-слоя.

Для integration и e2e тестов используется реальный PostgreSQL:

* локально и в CI — через Docker Compose сервис `postgres-test` либо Testcontainers;
* каждый тестовый прогон применяет полный набор migrations к чистой базе или чистой схеме;
* тестовые сьюты изолируются друг от друга через отдельную базу/схему на воркер либо через транзакцию с rollback в конце теста, где это применимо;
* тесты не должны зависеть от состояния, оставшегося после предыдущего прогона;
* тестовая база не используется для длительного хранения демонстрационных или production-подобных данных.

### Конфигурация

Используется единая переменная подключения:

```text
DATABASE_URL=postgresql://user:password@localhost:5432/svistoplyasovo
TEST_DATABASE_URL=postgresql://user:password@localhost:5432/svistoplyasovo_test
```

Конфигурация выбирается через NestJS `ConfigModule` и фабрику TypeORM DataSource. Прямые обращения к `process.env.DATABASE_URL` по всему коду запрещены — только через конфигурационный модуль.

### Общая модель

Для всех окружений используются:

* одни TypeORM entities;
* одни repository interfaces;
* одни application services;
* одни доменные правила;
* одни API-контракты.

Раздвоения кода или конфигурации по разным СУБД не предусмотрено.

### Использование возможностей PostgreSQL

Поскольку платформа не обязана поддерживать вторую СУБД, допустимо и приветствуется осознанное использование возможностей PostgreSQL там, где они реально улучшают надёжность и производительность:

* `jsonb` для полуструктурированных данных;
* массивы и range-типы, где это уместно предметно;
* database enum-типы либо check constraints;
* `ILIKE` и полнотекстовый поиск;
* partial indexes;
* exclusion constraints как дополнительная защита от конфликтов бронирования;
* materialized views для тяжёлых аналитических read models.

При этом сохраняется правило: любое бизнес-правило обязано быть проверено в application/domain-слое. Constraints, triggers и индексы PostgreSQL используются как дополнительный защитный слой (defense in depth), а не как единственный источник истины о допустимости операции. Такие решения фиксируются в `DECISIONS.md`.

### Идентификаторы, даты и деньги

* UUID генерируются приложением, а не зависят от функции базы данных;
* timestamps передаются и хранятся как UTC;
* бизнес-часовой пояс применяется в application/domain-слое;
* деньги хранятся целыми значениями;
* boolean, enum и JSON-структуры должны иметь явно проверяемое представление на уровне приложения;
* запрещено полагаться на неочевидные неявные преобразования типов базы данных.

### Транзакции и конкурентность

* транзакции инкапсулируются в отдельном transaction manager;
* application service не обращается к глобальному EntityManager напрямую в обход transaction manager;
* optimistic concurrency через `version` обязательна;
* операции, критичные к конкурентному доступу (создание/перенос бронирования, регистрация на программу, оплата), дополнительно защищены row-level locking или эквивалентным механизмом PostgreSQL;
* availability engine обязан быть протестирован в условиях параллельных запросов на реальном PostgreSQL (см. раздел 22.3);
* конфликт двух сотрудников считается неподтверждённым, пока не пройден соответствующий тест на реальном PostgreSQL.

## 4.4. Миграции и схема

### PostgreSQL

* `synchronize: false` во всех окружениях без исключений, включая тестовое;
* все изменения схемы оформляются явными TypeORM migrations;
* миграции хранятся в `packages/db/src/migrations/postgres`;
* миграции выполняются отдельно от старта web-приложения;
* тестовая база данных приводится к нужной схеме применением тех же migrations, что и production;
* rollback предусмотрен там, где он безопасен;
* destructive migration требует отдельного плана сохранения данных;
* автогенерация миграции допустима только как заготовка с обязательной ручной проверкой.

### Тестовая база данных

* тестовая PostgreSQL база создаётся заново или полностью очищается перед прогоном тестового набора (полный `migration:run` на чистую базу/схему);
* `synchronize: true` не используется даже в тестах — миграции обязаны быть проверены тем же способом, что и в production;
* тесты не зависят от сохранения состояния базы между запусками;
* параллельные тестовые воркеры используют отдельные базы данных или схемы, чтобы не конфликтовать друг с другом.

### Обязательные scripts

```text
pnpm dev
pnpm build
pnpm lint
pnpm typecheck
pnpm test
pnpm test:unit
pnpm test:integration
pnpm test:e2e
pnpm db:migrate
pnpm db:revert
pnpm db:seed
```

`pnpm test` должен запускать unit tests и integration tests против PostgreSQL. Наличие поднятой тестовой PostgreSQL базы (локально или через Docker Compose/Testcontainers) является обязательным условием прогона `pnpm test`. Production-ready статус дополнительно требует успешного прогона тестов конкурентности и блокировок (раздел 22.3).

## 4.5. Чеклист готовности production-окружения

Поскольку PostgreSQL используется на всех этапах разработки, отдельного этапа «миграции с другой СУБД» не требуется. Тем не менее перед первым production deployment и перед каждым значимым релизом необходимо подтвердить готовность:

1. поднята PostgreSQL поддерживаемой версии в production-конфигурации (ресурсы, параметры соединений, бэкапы/репликация по необходимости);
2. все migrations применены на актуальную базу в правильном порядке;
3. выполнен seed системных справочников и ролей;
4. пройден полный набор `pnpm test:integration` против PostgreSQL;
5. пройдены end-to-end tests против PostgreSQL;
6. проверены индексы и планы выполнения критических запросов;
7. проверено конкурентное создание и перенос бронирований под нагрузкой, близкой к реальной;
8. проверены timezone, поиск без учёта регистра, JSON-поля и сортировка на реальных данных;
9. настроены backup, restore test и retention policy;
10. зафиксирован rollback-план на случай неудачного релиза (миграции с безопасным откатом либо отдельный план для деструктивных изменений).

## 4.6. Дизайн-система: обязательное использование официального shadcn/ui CLI и preset `bIkezqK`

### 4.6.1. Принцип

UI-примитивы CRM (а в перспективе — и технической админки) обязаны быть буквально сгенерированным исходным кодом shadcn/ui на базе Radix UI, сконфигурированным пресетом Vega `bIkezqK`, а не визуальной имитацией этого пресета.

**Запрещено:**

* создавать собственные компоненты `ui-button`, `ui-input`, `ui-dialog`, `ui-select`, `ui-tabs`, `ui-card` и подобные, вручную воспроизводящие внешний вид Vega через Tailwind-классы или самописный CSS;
* подключать только CSS-переменные, цветовую палитру, радиусы и типографику preset'а и поверх них рисовать произвольную, самостоятельно написанную разметку компонентов;
* заменять сгенерированные компоненты «похожими» библиотечными аналогами (Material UI, Ant Design, Chakra и т.п.) со стилизацией под Vega.

Компонент считается корректно подключённым только тогда, когда это тот самый файл (`button.tsx`, `dialog.tsx`, `select.tsx`, `tabs.tsx`, `command.tsx`, `sheet.tsx`, `table.tsx`, `form.tsx`, `calendar.tsx`, `badge.tsx`, `dropdown-menu.tsx`, `popover.tsx`, `tooltip.tsx`, `switch.tsx`, `radio-group.tsx`, `accordion.tsx`, `sonner.tsx` и т.д.), который генерирует официальный CLI `shadcn` с применённым preset `bIkezqK`, включая внутреннее использование соответствующих Radix-примитивов и `cva`-вариантов.

### 4.6.2. Обязательная последовательность действий перед реализацией фронтенда

До начала (или при расширении) реализации UI любого этапа агент обязан выполнить следующие шаги, в указанном порядке, и зафиксировать результат в `DECISIONS.md`:

1. **Декодировать preset.**
   Выполнить:

   ```text
   pnpm dlx shadcn@latest preset decode bIkezqK --json
   ```

   Сохранить результат как артефакт конфигурации проекта (например, `packages/ui/preset/bIkezqK.json`) — тему, radius, токены, состав компонентов и вариантов пресета.

2. **Получить компоненты официальным способом.**

   * Если структура репозитория позволяет — выполнить `shadcn init` и далее `shadcn add <component>` (либо `shadcn apply` с preset `bIkezqK`) непосредственно в целевом workspace (`apps/crm` или `packages/ui`).
   * Если текущий репозиторий — монорепозиторий и прямая инициализация CLI конфликтует со структурой `pnpm workspaces` (конфликты `components.json`, путей алиасов, версий Tailwind и т.д.) — поднять временный чистый Vite-проект вне основного дерева монорепозитория (или во временной директории), выполнить в нём `shadcn init` с preset `bIkezqK` и сгенерировать там необходимый набор компонентов.

3. **Перенести именно сгенерированные файлы.**
   Файлы компонентов, полученные CLI (без ручного переписывания их содержимого), переносятся в `packages/ui/src/components/ui` с сохранением оригинальной структуры shadcn. Вместе с ними переносятся/синхронизируются: `components.json`, Tailwind-конфигурация, CSS-переменные темы, утилита `cn`, зависимости Radix, использованные конкретными компонентами.

4. **Удалить временный инструмент генерации.**
   Временный Vite-проект (если использовался) не остаётся частью репозитория — он существует только как инструмент генерации кода и удаляется после переноса файлов.

5. **Не заменять generated components обёртками.**
   Допускается только:

   * тонкая композиция generated-примитивов в доменные виджеты (например, `BookingStatusBadge`, `ResourceTimelineCard`, `ConflictBanner`, `EntityCategoryBadge`), которые используют `Badge`, `Button`, `Card`, `Popover`, `Tooltip` и другие generated-компоненты как строительные блоки, не переопределяя их внутреннюю разметку и не дублируя их стили вручную;
   * точечная кастомизация через официально поддерживаемые механизмы shadcn/ui — `cva`-варианты, проп `className`, Tailwind-конфигурация, CSS-переменные темы, — но не переписывание разметки компонента с нуля.

6. **Сохранить бизнес-логику и экраны.**
   Вся существующая бизнес-логика, маршруты, состояние, работа с API и данные приложения сохраняются без изменений. Меняются только UI-примитивы (кнопки, поля ввода, диалоги, таблицы, вкладки, попапы, календарь, командная палитра, переключатели и т.д.) — они заменяются на сгенерированные аналоги с сохранением поведения, доступности и существующих сценариев использования.

### 4.6.3. Обязательная финальная проверка

Этап (или соответствующая часть этапа), затрагивающий UI, не может считаться выполненным, пока не подтверждено следующее:

* импорты UI-примитивов в приложении фактически указывают на файлы, полученные генерацией из preset `bIkezqK` (например, `@ui/components/ui/button`), а не на параллельные самописные компоненты с похожими именами и API;
* файлы в `packages/ui/src/components/ui` структурно и по происхождению соответствуют тому, что создаёт официальный CLI shadcn (наличие Radix-примитивов внутри, стандартных `cva`-вариантов, стандартного набора пропсов);
* **простое совпадение CSS-переменных, цветовой палитры или radius с темой Vega не является достаточным доказательством выполнения требования.** Обязательно должно быть предъявлено подтверждение происхождения исходного кода: вывод `preset decode`, сохранённый `components.json`, история добавления файлов через `shadcn add`/`shadcn apply`, либо diff, показывающий перенос файлов из сгенерированного источника;
* в `DECISIONS.md` зафиксированы: факт применения preset `bIkezqK`, список сгенерированных и подключённых компонентов, использованный способ генерации (прямой `init` в workspace либо через временный Vite-проект) и итоговое расположение файлов в `packages/ui`.

### 4.6.4. Расширение UI-кита

Добавление новых компонентов shadcn в последующих этапах (по мере появления новых экранов) выполняется той же процедурой: `shadcn add <component>` с использованием сохранённой preset-конфигурации `bIkezqK`, перенос сгенерированных файлов в `packages/ui`, без ручной имитации новых компонентов.

### 4.6.5. Продуманное проектирование фронтенда поверх дизайн-системы

Применение официального preset задаёт исходный код и визуальный язык компонентов, но не проектирует сами экраны. Перед реализацией каждого экрана — и в первую очередь экранов, связанных с настройками, конфигурацией отображения и представлением больших объёмов данных (списки, таблицы, scheduler, dashboard, формы с большим количеством полей, панели фильтров) — агент обязан:

* спроектировать информационную архитектуру экрана (что первично, что второстепенно, что скрыто за дополнительным действием);
* продумать состояния экрана: пусто, загрузка, частичная загрузка, ошибка, конфликт, много данных, права ограничены;
* выбрать конкретные generated-компоненты исходя из семантики задачи, а не произвольно (см. также раздел 12.6 и 12.7);
* предусмотреть отзывчивое поведение (desktop/tablet/mobile) и то, как элемент управления или таблица ведут себя при нехватке места;
* приоритетно рассмотреть замену текстовой подписи компактной иконкой с `Tooltip` там, где действие общепринято и не создаёт риска неверного толкования (детальные правила — раздел 12.7);
* убедиться, что решение не противоречит принципам раздела 12 (route-driven overlay, единый вход создания, отсутствие цвета как единственного статуса, визуальная идентификация категорий по разделу 6.11 и т.д.).

# 5. Архитектурные принципы

## 5.1. Full-stack vertical slices

Каждая функция реализуется целиком.

Например, «создание заявки» включает:

* таблицы и миграции;
* backend validation;
* API endpoint;
* права;
* idempotency;
* frontend-форму;
* обработку ошибок;
* сохранение;
* optimistic state;
* audit log;
* тесты.

Нельзя считать функцию реализованной, если форма визуально существует, но после перезагрузки данные исчезают.

## 5.2. Backend authoritative

Frontend может:

* предварительно валидировать форму;
* показывать preview;
* временно отображать optimistic state;
* блокировать очевидно недоступные действия.

Окончательное решение всегда принимает backend.

## 5.3. Общие контракты

API-типы не дублируются вручную в разных приложениях.

Одна схема должна использоваться для:

* backend validation;
* OpenAPI;
* frontend client;
* формы;
* server error mapping;
* тестов.

## 5.4. Модульный монолит

На первом этапе использовать модульный монолит, а не микросервисы.

Основные backend-модули:

```text
auth
users
permissions
leads
customers
tasks
resources
availability
bookings
programs
events
payments
notifications
search
audit
content
integrations
```

Модули должны иметь ясные границы, но работать в одном приложении и одной транзакционной модели.

Микросервисы для масштаба одной базы отдыха — это не архитектура, а дорогостоящий способ размазать ошибки по сети.

## 5.5. Границы NestJS-модулей

Каждый предметный NestJS-модуль должен экспортировать только явно определённый application API.

Запрещено:

* импортировать TypeORM repository другого модуля напрямую;
* обращаться к entity другого модуля как к общей изменяемой структуре;
* создавать циклические зависимости между модулями;
* решать циклическую зависимость бесконтрольным использованием `forwardRef`;
* помещать всю бизнес-логику в один `CommonService`;
* превращать `shared` или `common` в свалку несвязанных функций.

Связь модулей выполняется через:

* application services;
* явно определённые ports;
* доменные события;
* outbox events для внешних эффектов;
* read models для агрегирующих экранов.

## 5.6. Зависимости слоёв

Допустимое направление зависимостей:

```text
controller
  → application service / use case
    → domain rules and repository ports
      ← TypeORM repository adapters
```

Недопустимое направление:

```text
domain → NestJS
contracts → TypeORM
frontend → database entities
controller → TypeORM repository
entity → React form
```

TypeORM entity не является API DTO. Возврат entity напрямую из controller запрещён.

* `SavedView`;
* `ChangeLogEntry`;

## 6.2. Заявка

`Lead` хранит потенциальный интерес клиента.

Примерные данные:

* клиент или ещё не связанный контакт;

## 6.3. Клиент

`Customer` может представлять:

* физическое лицо;
* компанию;
* организатора;
* постоянного клиента.

Необходимо предусмотреть:

* несколько телефонов и каналов;
* дедупликацию;
* объединение дублей;
* историю обращений;
* посещения;
* брони;
* оплаты;
* долг;
* ответственного;
* согласия на обработку данных.

## 6.4. Бронь

`Booking` является общим агрегатом заказа.

Одна бронь может содержать несколько `BookingItem`.

Пример смешанной брони:

* домик;
* баня;
* чан;
* банкетный зал;
* сцена;
* палатка;
* место под палатку;
* проведение программы;
* дополнительная услуга.

Каждая позиция может иметь:

* собственный ресурс;
* начало;
* окончание;
* количество;
* стоимость;
* скидку;
* подготовку до и после;
* правила вместимости;
* комментарий.

## 6.5. Ресурсы

### Проживание

* Дом на дереве;
* Дом-гнездо.

### Баня и водные услуги

* Баня;
* Чан.

### Площадки

* Банкетный зал;
* Веранда;
* Беседка «Деда Никулы»;
* Юрта;
* Сцена.

### Палаточный кемпинг

Инвентарные ресурсы:

* Лесная деревянная палатка;
* Палатка советская;
* Палатка классическая;
* Палатка Деда Никулы.

Ёмкостный ресурс:

* Общее место под палатку.

Для ёмкостного ресурса backend хранит `capacity`, а расписание показывает:

```text
занято X / Y
```

Каждый ресурс и каждая группа ресурсов маркируются иконкой и цветом по правилам раздела 6.11 — это позволяет отличать домики, баню и чан, площадки и палатки друг от друга визуальным сканированием расписания, а не только чтением подписей.

## 6.6. Единое ядро занятости ресурсов

Необходимо ввести системную сущность `ResourceAllocation`.

Она нормализует все интервалы, влияющие на доступность:

* позиции бронирования;
* мероприятия;
* проведения программ;
* регистрации;
* технические блокировки;
* подготовительные интервалы.

Примерная структура:

```text
id
resourceId
sourceType
sourceId
startAt
endAt
quantity
capacityImpact
status
version
```

Все scheduler-представления и проверки доступности должны использовать единый availability-модуль.

Нельзя отдельно проверять конфликты для брони, отдельно для программы и отдельно для мероприятия. Иначе система неизбежно разрешит двум разным модулям занять один ресурс.

## 6.7. Мероприятие

`Event` является специализированной сложной бронью.

Мероприятие может включать:

* несколько ресурсов;
* независимые интервалы;
* программу;
* услуги;
* этапы подготовки;
* задачи;
* оплату;
* проживание;
* оборудование.

`Event` не должен создавать параллельную систему резервирования. Он использует `Booking`, `BookingItem` и `ResourceAllocation`.

Тип/направление мероприятия (`Event.type`) маркируется иконкой и цветом по правилам раздела 6.11.

## 6.8. Программы

Разделять:

* `ProgramTemplate` — шаблон;
* `ProgramOccurrence` — конкретное проведение;
* `ProgramRegistration` — регистрация клиента или группы.

Проведение может:

* занимать ресурс;
* иметь лимит;
* содержать регистрации;
* иметь оплату;
* быть перенесено;
* быть отменено;
* быть закрыто для регистрации.

Категория `ProgramTemplate` маркируется иконкой и цветом по правилам раздела 6.11.

## 6.9. Платежи

Платёжные операции являются неизменяемыми.

Нельзя редактировать проведённую операцию задним числом.

Коррекция выполняется:

* возвратом;
* компенсирующей операцией;
* отдельной корректировкой с причиной.

Суммы должны храниться в минимальных денежных единицах, а не в `float`.

Статус оплаты рассчитывается отдельно от жизненного статуса брони.

Примеры:

* не оплачено;
* частично оплачено;
* оплачено;
* переплата;
* возврат;
* задолженность.

## 6.10. Системные поля

Каждая изменяемая сущность должна иметь:

```text
id
version
createdAt
createdBy
updatedAt
updatedBy
archivedAt
```

Физическое удаление исторических операционных данных не использовать.

## 6.11. Визуальная идентификация категориальных сущностей (иконка и цвет)

Многие справочные и категориальные сущности платформы (ресурсы и их группы, категории программ, типы мероприятий и т.п.) постоянно встречаются рядом друг с другом — в scheduler, канбане, списках, dashboard, карточках. Чтобы сотрудник мог отличать их не только по тексту, но и визуальным сканированием (боковым зрением, при беглом просмотре плотного расписания), для таких сущностей необходимо предусмотреть настраиваемую пару полей:

```text
icon
color
```

Требования:

* `icon` — идентификатор иконки из набора Lucide Icons (либо ограниченного курируемого подмножества), выбираемый через административный интерфейс/настройки CRM, а не жёстко прошитый на frontend;
* `color` — значение из ограниченной согласованной палитры, совместимой с токенами preset `bIkezqK`, а не произвольный HEX — чтобы сохранить визуальную целостность дизайн-системы;
* комбинация «иконка + цвет» является меткой категоризации/идентификации сущности (её типа, группы, направления), а не статусом, и не должна смешиваться с индикацией статуса, описанной в разделе 12.5: статус брони/заявки/оплаты по-прежнему выражается минимум двумя признаками (текст, цвет, форма), а иконка и цвет ресурса/категории — отдельный, параллельный визуальный слой;
* значения иконки и цвета никогда не являются единственным способом идентификации — рядом всегда присутствует текстовое название либо доступный `Tooltip` (см. раздел 20 про доступность).

Минимальный обязательный охват сущностей, для которых предусматриваются иконка и цвет:

* `Resource` и `ResourceGroup` (домики, баня и чан, площадки, палаточный кемпинг и т.д.);
* категория `ProgramTemplate`;
* тип/направление `Event`;
* при развитии продукта — направление `Lead`, тип `Task`, причина `ResourceBlock`.

Архитектурные требования:

* на backend это дополнительные поля соответствующих entities и DTO, проверяемые Zod-схемой (ограниченный enum допустимых иконок и enum/палитра допустимых цветов, а не произвольная строка);
* значения по умолчанию задаются при создании справочника/сущности и могут быть изменены только через настройки CRM или административный интерфейс, с учётом раздела 12.6 (подтверждение изменений, влияющих на многих пользователей);
* на frontend вводится единый переиспользуемый доменный компонент идентификации (например, `EntityCategoryTag`/`EntityBadge`) в `packages/ui/src/components/domain`, построенный поверх сгенерированных примитивов (`Badge`, `Tooltip`, иконки Lucide) без ручного дублирования их разметки;
* этот компонент используется во всех представлениях, где фигурирует соответствующая сущность: канбан, scheduler (заголовки групп ресурсов, карточки), списки, таблицы, dropdown/`Command` выбора ресурса или категории, карточки мероприятий и программ;
* там, где на одном экране одновременно присутствует индикация статуса и индикация категории (например, карточка брони показывает и тип ресурса, и статус брони), они визуально разделяются формой представления (например, цветная точка/иконка слева — категория, `Badge` статуса — отдельно), чтобы не создавать двусмысленность;
* для экранов настройки справочников предусматривается общий `Legend`-компонент — список категорий/типов с их иконкой, цветом и названием, — который может быть показан рядом со scheduler или списком при необходимости.

# 12. UX-принципы CRM

## 12.1. Редактирование вместо просмотра

Рабочие сущности открываются сразу в режиме редактирования.

Исключения:

* архив;
* readonly;
* системная история;
* проведённые финансовые операции;
* отсутствие разрешения.

## 12.2. Route-driven overlay

Сущность открывается в `EntityEditorOverlay` поверх текущего экрана.

Overlay:

* создаётся через portal в `body`;
* обновляет URL;
* поддерживает прямую ссылку;
* закрывается через browser Back;
* сохраняет background location;
* возвращает дату;
* сохраняет scroll;
* сохраняет фильтры;
* сохраняет выбранное представление.

Desktop:

* centered overlay;
* перекрывает sidebar и topbar;
* фиксированный header;
* sticky tabs;
* прокручиваемый body;
* фиксированный action bar.

Mobile:

* `inset: 0`;
* выше всей навигации;
* safe area;
* fullscreen;
* фиксированная кнопка сохранения.

`Sheet` или правый inspector не использовать как основной редактор сущности.

## 12.3. Один глобальный вход создания

Desktop:

* одна кнопка `+ Создать` в topbar.

Mobile:

* один центральный пункт `Создать` в bottom navigation.

Разрешены контекстные действия:

* создать бронь из интервала;
* добавить оплату;
* добавить позицию;
* добавить регистрацию;
* поставить задачу;
* создать бронь из заявки.

Контекстные действия должны иметь конкретное название.

## 12.4. YCLIENTS как операционный ориентир

Использовать следующие принципы:

* плотное расписание;
* минимальное количество переходов;
* быстрое открытие записи;
* редактирование поверх расписания;
* разделение ресурсов;
* создание из свободного интервала;
* фиксированные управляющие области.

Визуальное копирование YCLIENTS не требуется.

## 12.5. Цвет не является данными

Статус выражается минимум двумя признаками:

* текст;
* цвет;
* иконка;
* форма badge;
* контур.

Статус брони и статус оплаты не объединяются.

Отдельно от статуса, категориальные сущности (ресурсы, категории программ, типы мероприятий) получают собственную цветовую и иконочную маркировку по правилам раздела 6.11 — это самостоятельный визуальный слой идентификации типа/группы, а не индикация состояния, и он не должен подменять или смешиваться с индикацией статуса, описанной в этом разделе.

## 12.6. Проектирование экранов настроек и отображения

Использование preset `bIkezqK` и сгенерированных через официальный CLI компонентов shadcn/ui задаёт исходный код и визуальный язык интерфейса, но не проектирует сами экраны. Preset не избавляет агента от необходимости самостоятельно продумывать информационную архитектуру, поведение и удобство конкретных экранов — особенно тех, что связаны с настройками и с отображением данных.

Для любых настроек CRM (сохранённые представления, фильтры, видимые колонки таблиц, масштаб scheduler, параметры уведомлений, настройки ролей, системные параметры и т.д.) обязательны следующие принципы:

* настройки группируются по смысловому контексту, а не по техническому происхождению поля;
* каждая настройка имеет понятное название и, где уместно, краткое описание эффекта;
* изменение настройки, где это уместно, сопровождается мгновенным или отложенным предпросмотром результата (например, изменение масштаба scheduler, изменение набора видимых колонок таблицы);
* сохранённые представления (`SavedView`) явно визуально и функционально отделены от временных фильтров текущей сессии;
* настройки, влияющие на других пользователей или на большой объём данных (роли, права, системные параметры, публикация), сопровождаются подтверждением и понятным описанием последствий;
* персональные настройки пользователя (масштаб, порядок и ширина колонок, свёрнутые группы, последнее выбранное представление) хранятся отдельно от общих командных настроек;
* для длинных списков настроек (раздел «Настройки CRM», управление ролями и правами) предусмотрены поиск и/или структурная навигация, а не одна длинная страница;
* незавершённое изменение настроек отображается тем же паттерном dirty state, что и в overlay-редакторах сущностей (раздел 15.1);
* на mobile длинные формы настроек разбиваются на логические секции с навигацией между ними, а не превращаются в одну длинную прокручиваемую форму без ориентиров;
* выбор конкретного generated-компонента для настройки определяется её семантикой, а не произвольно: переключатель да/нет — `Switch`; выбор одного значения из небольшого фиксированного набора — `RadioGroup` или `Select`; выбор из длинного списка с поиском — `Command`/`Combobox`; группировка логически связанных настроек — `Accordion` или `Tabs`; массовые действия и подтверждения — `AlertDialog`; выбор иконки и цвета для категориальной сущности (раздел 6.11) — специализированный `IconPicker`/`ColorPicker` на базе `Popover` + `Command`.

Экраны отображения данных (списки, таблицы, dashboard, scheduler) дополнительно обязаны учитывать состояния: пусто, загрузка, частичная загрузка, ошибка, нет прав, слишком много данных для текущего представления — и предлагать пользователю понятный следующий шаг в каждом из этих состояний.

## 12.7. Компоновка панели фильтров и параметров отображения

Панель фильтров и связанных с ней элементов управления отображением (переключение вида, масштаб, выбор сохранённого представления, настройка видимых колонок/полей карточки) по умолчанию проектируется так, чтобы приоритетно помещаться в одну строку на desktop-разрешении, а не превращаться в громоздкую многострочную панель управления.

Обязательные принципы:

* при проектировании панели сначала определяется минимально необходимый набор управляющих элементов, которые должны быть видны постоянно; второстепенные фильтры выносятся в дополнительное меню (`Popover`/`Sheet` с фильтрами, кнопка «Ещё фильтры») вместо переноса панели на вторую строку;
* для управляющих элементов с общепринятым и однозначным смыслом (обновить данные, настроить видимые колонки, экспорт, переключение вида список/канбан/timeline, сохранить представление, поделиться ссылкой, открыть легенду категорий) приоритетно используется компактная иконка с обязательным `Tooltip` вместо текстовой подписи;
* текстовая подпись сохраняется там, где действие не является общепринятым, влечёт необратимые последствия или затрагивает других пользователей (архивирование, публикация, массовое изменение, удаление сохранённого представления), либо где значение иконки неоднозначно вне контекста;
* если совокупность необходимых элементов управления объективно не помещается в одну строку на desktop, вместо перехода на вторую строку приоритетно применяются: схлопывание редко используемых фильтров в `DropdownMenu`/`Popover`, горизонтальный скролл с явной визуальной подсказкой о наличии дополнительных элементов, либо adaptive-скрытие наименее приоритетных элементов с явным индикатором «есть скрытые фильтры»;
* для длинных списков и таблиц (клиенты, брони, задачи и т.д.) панель обязана включать управление отображением столбцов — показать/скрыть столбец, изменить порядок, закрепить столбец — реализуемое через `DropdownMenu`/`Popover` с чекбоксами и drag-переупорядочиванием, без перехода на отдельную страницу настроек;
* для карточных представлений (канбан заявок, карточки мероприятий, карточки клиентов на mobile) панель аналогично даёт возможность выбрать, какие поля отображаются внутри карточки (например, показать/скрыть долг, ближайшую бронь, источник) — через тот же паттерн компактного меню настроек отображения;
* видимость и порядок столбцов/полей карточки — персональная настройка пользователя (раздел 12.6), хранится отдельно от общих `SavedView`, но может быть включена в состав `SavedView` при явном сохранении представления;
* на mobile, где панель фильтров физически не помещается в одну строку, применяется тот же принцип приоритизации: 1–2 наиболее часто используемых фильтра остаются видимыми, остальные скрываются за одной кнопкой «Фильтры» с индикатором количества применённых фильтров;
* при проектировании каждого конкретного экрана со списком/таблицей/канбаном/scheduler агент обязан явно спроектировать раскладку панели управления — какие элементы остаются иконками с `Tooltip`, какие требуют текстовой подписи, какие уходят в дополнительное меню — и зафиксировать это решение при проектировании этапа, а не полагаться на автоматическое перетекание элементов на новую строку.

# 22. Тестирование

## 22.1. Unit tests

Backend unit tests выполняются на Jest без подключения реальной базы там, где это возможно.

Frontend unit tests выполняются на Vitest.

Проверяют:

* пересечения интервалов;
* вместимость;
* цены;
* статусы;
* переходы;
* debt calculation;
* permissions;
* idempotency;
* сериализацию контрактов;
* mapping доменных ошибок в API errors.

## 22.2. Integration tests (PostgreSQL)

Интеграционные тесты выполняются против реального PostgreSQL — через Docker Compose сервис `postgres-test` либо Testcontainers. Отдельной «быстрой» СУБД для тестов не используется: чем ближе тестовая среда к production, тем меньше риск скрытых несовместимостей.

Проверяются:

* NestJS modules;
* controllers;
* Zod validation pipes;
* guards;
* interceptors;
* exception filters;
* TypeORM repositories;
* API;
* CRUD;
* транзакционный rollback;
* связи и foreign keys;
* optimistic version checks;
* idempotency;
* payments;
* availability;
* audit;
* outbox persistence.

Требования:

* отдельная база данных или схема на test suite либо test worker;
* миграции применяются перед прогоном тестового набора;
* отсутствие зависимости от порядка тестов;
* воспроизводимый seed;
* отсутствие обращения к внешним сервисам;
* очистка ресурсов после выполнения.

## 22.3. Тесты конкурентности и блокировок PostgreSQL

Отдельный набор тестов (может запускаться реже, например перед релизом, но обязан существовать и быть воспроизводимым в любой момент) нацелен на сценарии, критичные именно для production-конкурентности:

* применение всех migrations с нуля;
* повторный запуск migration pipeline;
* row-level locking;
* конкурентные записи и создание пересекающихся бронирований;
* optimistic concurrency под параллельной нагрузкой;
* уникальные и составные indexes, exclusion constraints;
* foreign keys и constraints;
* case-insensitive search;
* timezone и timestamp semantics;
* JSON serialization;
* cursor pagination на больших наборах данных;
* query plans критических выборок;
* availability conflicts при одновременных операциях;
* outbox claiming несколькими worker-процессами.

Каждый этап обязан предоставить запускаемый `pnpm test:integration`, покрывающий, где применимо, сценарии этого раздела, даже если текущая среда агента не позволяет поднять PostgreSQL контейнер локально.

Если тесты против PostgreSQL не запускались, это явно фиксируется в `KNOWN-LIMITATIONS.md`. Этап может считаться пригодным для продолжения разработки, но не production-ready.

## 22.4. End-to-end tests

Playwright запускается против реально поднятых frontend, NestJS API и PostgreSQL.

Минимальные сценарии:

1. вход;
2. создание заявки;
3. создание клиента;
4. создание брони;
5. добавление нескольких позиций;
6. проверка конфликта;
7. перенос брони;
8. resize;
9. регистрация оплаты;
10. создание проведения программы;
11. открытие прямой ссылки на overlay;
12. возврат в исходный scroll;
13. работа на mobile viewport;
14. конфликт двух пользователей.

Все e2e-сценарии выполняются против PostgreSQL — отдельного «быстрого» набора на другой СУБД не предусмотрено. Перед production release критические сценарии обязательно повторяются в окружении, максимально близком к production.

## 27.1. Технические критерии

* используется единая база данных — PostgreSQL — во всех окружениях: разработка, тесты, staging, production;
* одна предметная модель и один набор TypeORM entities;
* типизированные API-контракты;
* бизнес-правила находятся на backend;
* отсутствуют дублирующие механизмы занятости;
* платежи неизменяемы;
* операции идемпотентны;
* используется optimistic concurrency;
* права проверяются backend;
* PostgreSQL migrations воспроизводимы;
* seed воспроизводим;
* unit и integration tests (против PostgreSQL) проходят;
* тесты конкурентности и блокировок PostgreSQL (раздел 22.3) существуют и проходят перед production release;
* build проходит;
* архив запускается по README;
* business/domain-слой не зависит от деталей TypeORM и способа хранения данных;
* API не возвращает TypeORM entities напрямую;
* `synchronize: true` отсутствует в production, staging и тестовом окружении;
* UI-примитивы CRM являются исходным кодом, сгенерированным официальным shadcn CLI с preset `bIkezqK`, а не самописной имитацией (раздел 4.6);
* происхождение UI-компонентов подтверждено на уровне исходного кода (импорт-путей и структуры файлов), а не только совпадением CSS-токенов и темы;
* категориальные сущности (ресурсы, категории программ, типы мероприятий) имеют настраиваемые поля иконки и цвета, используемые единым компонентом идентификации на всех экранах (раздел 6.11).

# 29. Главные запреты

1. Не создавать frontend отдельно от backend.
2. Не использовать mock-данные как основной runtime.
3. Не дублировать бизнес-правила на клиенте.
4. Не создавать несколько таблиц занятости для разных модулей.
5. Не разрешать сайту прямой доступ к базе.
6. Не редактировать проведённые платежи.
7. Не перезаписывать конкурентные изменения молча.
8. Не использовать правый inspector вместо общего overlay.
9. Не создавать несколько глобальных кнопок «Создать».
10. Не превращать mobile в уменьшенный desktop scheduler.
11. Не использовать цвет как единственный статус.
12. Не вводить микросервисы без доказанной необходимости.
13. Не считать задачу законченной, пока данные не сохраняются после перезагрузки.
14. Не оставлять кнопки и формы декоративными.
15. Не менять preset и дизайн-систему без явного решения проекта.
16. Не использовать `synchronize: true` вне полностью изолированной тестовой базы данных.
17. Не писать raw SQL в обход repository-слоя без явного обоснования и фиксации решения в `DECISIONS.md`.
18. Не использовать возможности PostgreSQL (constraints, triggers, exclusion constraints) как единственный механизм проверки бизнес-правила — оно обязано быть также реализовано в domain/application-слое.
19. Не возвращать TypeORM entities напрямую из controllers.
20. Не обращаться к repositories из controllers в обход application service.
21. Не запускать production schema migrations автоматически при старте каждого API-инстанса.
22. Не хранить тестовые или демонстрационные данные в production базе данных.
23. Не откладывать создание PostgreSQL migrations: они создаются одновременно с каждым изменением entities.
24. Не имитировать компоненты Vega/shadcn самописными CSS-классами, кастомными `ui-button`, `ui-input`, `ui-dialog` и подобными обёртками вместо получения их официальным CLI `shadcn` из preset `bIkezqK` (раздел 4.6).
25. Не считать совпадение цветовой темы, CSS-переменных или токенов достаточным доказательством использования preset `bIkezqK` — обязательна проверка происхождения исходного кода компонентов (сгенерированные файлы, а не только визуальное сходство).
26. Не полагаться только на текстовое название при различении ресурсов, категорий программ и типов мероприятий — обязательна дополнительная настраиваемая иконка и цвет (раздел 6.11), не подменяющие индикацию статуса.
27. Не превращать панель фильтров и настроек отображения в многострочную панель по умолчанию — сначала должны быть исчерпаны варианты схлопывания в меню, иконок с `Tooltip` и adaptive-скрытия (раздел 12.7).
